# 스피크이지 구현 경계

[규칙과 자료 확인](./SPEAKEASY_GAME_RULES.md)을 따른다. 현재는 원작 규칙의 순수 서버 모듈과 별도 규칙의 컴퓨터 상대 11턴 연습 대국을 제공한다. **멀티플레이 기본판은 아직 활성화하지 않는다.**

## 책임

- `packages/shared/src/games/speakeasy`: 직렬화 가능한 공개 건물·화면 DTO, 입력 enum. 서버 전체 state나 덱 순서는 export하지 않는다.
- `apps/server/src/games/speakeasy/domain`: 지불, 영업, 건설·증축·인수, 생산, 운송, 판매, 보호, 수준 증가, 방어, 목표 조건, 지역/최종 정산. 순수 함수가 복제한 candidate를 만들며 실패하면 원본을 보존한다.
- `apps/web/src/features/speakeasy`: 지도 중심 React 화면, 개인판, 대상/결과 검토, 키보드·터치, 영업 상태와 주류 표시, 효과음, 모션 감소.
- 처음에는 홈의 별도 **개발 미리보기**로 접근한다. 공개 게임 종류·room state·게임 시작에 미검증 기본판을 추가하지 않는다. 현재 홈 진입은 아래의 별도 연습 대국으로 연결되며, 기존 미리보기 컴포넌트는 고정된 예시다.

경제 모듈 함수는 전체 행동을 완성하는 서비스가 아니라 검증 가능한 하위 계산이다. 서버에서 주입할 생산량·판매 단가·이동 그래프·배당표와 행동 권한을 인자로 받는다. 전체 자동 초기 설정, 카드·개인판 개별 보너스, 개별 악명 보상 데이터와 모든 원작 장소의 전체 행동 구성은 아직 연결하지 않았다. 일반 장소의 행동 순서 큐와 지원 행동은 아래에서 연결한다. 아래 준비 라운드는 검증된 초기 구성물을 받아 첫 건물·운영 카드 선택을 연결한다. 이 함수를 Socket.IO 입력에 직접 연결하면 안 된다. `nextSpeakeasyTurn`은 라운드 경계 분류이며 `round-lifecycle.ts`가 필수 운영 카드 뽑기와 레스토랑 수익·차례 정산을 처리한다.

## 원작 보드 준비

`domain/board-setup.ts`의 `prepareSpeakeasyBoard`는 서버에서 서로 독립적으로 섞은 구역 순서와 검증된 초기 A 마피아 타일을 받아 인원별 구역·건물 칸·초기 마피아/경찰 및 막별 등장 구역을 만든다. 2인 폐쇄 구역 선택에서 권역별 2/2/1 제한을 적용하고, 정원을 채워 건너뛴 타일은 마피아 배치에서 제외하지 않는다. 경찰 순서는 폐쇄 구역과 독립적이다.

입력은 구역 1–16의 완전한 순열이어야 하며 중복·누락·잘못된 인원·초기 마피아 수/ID를 거절한다. 셔플과 실제 카드 선택은 서버 호출자가 담당하며 이 함수는 난수나 시간을 직접 사용하지 않는다. 미래 구역 순서와 마피아 타일을 포함한 반환값은 서버 내부 자료이며 응답 DTO가 아니다. 검증된 `districts`는 기존 economy에, 막별 구역은 기존 Luciano 시작 함수에 전달할 수 있고 2/3/4인 연결 테스트로 검사한다.

보드 준비는 전체 대국 초기화가 아니다. 초기 마피아 개별 세력·효과, 플레이어 준비의 개별 보너스, 카드/도시 타일/목표/부두 배치와 전체 controller 연결은 남아 있다. 테스트의 마피아와 배당표는 예시이며 공식 catalog로 배포하지 않는다.

## 플레이어 준비 라운드

`domain/player-setup.ts`는 준비 완료 전용 상태를 관리한다. `startSpeakeasyPlayerSetup`은 서버에서 준비한 지도·도시 타일·카포·덱과 각 종류 1장씩 배분한 초기 손패를 받으며, 초기 현금 $15/금고 $30/다섯 수준 1과 아직 시작하지 않은 상태를 검사한다. 실제 구성물의 ID 생성, 셔플, 전체 초기 자원 배분 및 개별 보너스 catalog를 대신 생성하지 않는다.

2인은 차례 역순의 부두 조직원 배치를 먼저 모두 해결한다. 이후 2/3/4인 모두 역순으로 첫 주점/증류소 건설 → 해당 칸 도시 타일 획득 → 건물 보너스 → 첫 운영 카드 설치/상단 보너스를 처리한다. 마피아 인수·증축·나이트클럽/카지노는 초기 건설로 허용하지 않으며 현금으로 지불한다. 초기 카드 하단 행동과 통상 턴 종료 뽑기는 실행하지 않는다. 카포를 사용하지 않으며 모든 준비가 끝난 뒤 원래 차례의 첫 플레이어부터 1막을 시작한다.

공용 `SpeakeasySetupCommandSchema`는 부두 좌표, 본인 건물/카드 ID와 gameId/revision만 받는다. actor는 인증 호출자로부터 전달하고, 가격이나 보너스 handler는 클라이언트에서 받지 않는다. 서버 catalog에는 개별 부두/건물/카드의 완전히 해결된 보너스 처리기를 등록한다. 필수 추가 선택을 아직 해결하지 못한 효과는 실패로 반환하며, 누락한 catalog를 무효과로 간주하지 않는다. 초기 운영 카드 catalog는 상단 보너스만 받아 하단 행동을 실행하는 경로가 없다.

각 선택은 복제한 상태에서 비용·타일 이동·보너스·진행 기록을 함께 검증하고 revision을 한 번 증가시킨다. 실패 또는 처리기 예외 시 원본을 유지한다. 도시 타일 정의와 전체 인스턴스 보존을 검증한다. `completeSpeakeasyPlayerSetup`은 전원 준비 완료 시에만 일반 명령 서비스에 등록할 수 있는 게임 상태를 반환한다. 준비 중 내부 `flow`를 직접 등록하면 안 된다. 준비 명령의 방/세션/receipt·Socket.IO·화면 연결은 후속 작업이며 이 내부 상태를 클라이언트에 전송하지 않는다.

회귀 검증은 2/3/4인 역순 준비, 2인 부두 중복/순서, 빈칸·현금·소유권·단계·revision 검사, 도시 타일과 보너스 처리 순서, 준비 중 뽑기/카포 사용 없음, 실패 원자성과 일반 명령 서비스의 첫 차례 연결을 포함한다. 시험용 보너스/구성물을 실제 원작 catalog로 배포하지 않는다.

## 목표 타일 준비

`domain/goal-setup.ts`의 `prepareSpeakeasyGoals`는 서버가 따로 섞은 지역 목표 및 센트럴파크 A/B/C 묶음의 타일 ID·인쇄 번호를 받아 지역 3개와 공원 5개의 배치 순서를 결정한다. 지역과 공원의 번호 중복 검사는 독립적이며 공원에서는 A 두 장 → 중복을 건너뛴 B 두 장 → 중복을 건너뛴 C 한 장 순서다. 선택하지 않은 22개 타일은 반환 목록으로 보존한다.

총 9/21개 수량과 전체 ID 유일성을 검사하고 선택 가능한 서로 다른 번호가 부족하면 초기 설정 전체를 거절한다. A는 맨 위 두 장을 사용하므로 잘못된 중복 A 데이터를 다른 타일로 대체하지 않는다. A/B/C의 개별 목록·장수·조건·보너스는 아직 공식 catalog 확인이 필요하며 이 함수는 해당 값을 생성하지 않는다. 타일 ID로 서버 catalog와 연결할 준비 단계이며 실제 목표/장부 상태와 전체 게임 시작 controller 연결은 남아 있다. 반환값 전체는 서버 내부 자료이고 네트워크 응답이 아니다.

## 차례와 라운드 종료

`domain/round-lifecycle.ts`는 `PLAYING → DRAW_OPERATION → PLAYING/ROUND_END → PLAYING/LUCIANO/FINAL_SCORING`을 관리한다. 서버의 검증된 설정에서 시작하며 운영 덱 순서와 손패를 내부에 보관한다. 레스토랑 명령은 인증 actor, gameId/revision, 현재 차례, 빈 위치와 필요한 본인 카드 수를 검증한다. 선택 위치의 즉시 영향력 참조와 다음 라운드 실제 차례 순서를 구분한다. 영향력 비용표의 미확인 값은 추가하지 않았다.

장소 행동을 끝내는 내부 hook 이후에는 운영 카드 뽑기를 생략할 수 없다. 클라이언트는 덱 종류만 고르며 서버가 맨 위 카드를 가져온다. 버린 카드는 해당 덱 아래로 돌려 전체 인스턴스 ID를 보존한다. `commitSpeakeasyRoundEconomy`는 서버에서 권한과 효과를 검증한 경제 함수 결과만 통합하는 내부 경계다. 클라이언트가 계산한 상태를 받는 API로 노출하지 않는다.

라운드 종료에서는 아래 줄의 방문 여부로 카지노 현금을 모든 플레이어에게 한 번 지급하고 차례를 확정한다. 마지막 라운드도 이 정산을 거쳐야 최종 점수를 반환한다. JSON 복원은 단계·차례 말·덱 종류와 ID·정산 기록의 일관성을 검사한다. 각 성공은 복제한 candidate를 검증하고 revision을 한 번 올리며 실패는 원본을 유지한다.

이 하위 모듈은 장소 권한, 카포 배치, 도우미/카드 보너스를 대신하지 않는다. 전체 게임 controller가 해당 효과를 먼저 해결한 뒤 내부 hook을 호출해야 한다. `game-flow.ts`가 카포 배치와 Luciano 완료 후 다음 막 진입을 연결한다. 일반 장소의 지원 행동은 아래 처리기에 연결하며, 나머지 효과와 Socket.IO 연결은 남아 있다.

## 카포 배치와 막 연결

`domain/game-flow.ts`는 기존 round/Luciano 모듈을 하나의 내부 흐름으로 연결한다. 초기 경제·덱·카포 ID와 인원별 행동 자리는 검증된 서버 설정으로 받아야 한다. 공식 행동 자리 목록을 추정해서 생성하지 않는다. 현재 actor의 사용 가능한 카포만 빈 일반 자리에 놓을 수 있고, 레스토랑은 중복 점유가 가능하다. 레스토랑 배치와 필수 카드 지불·차례 선택은 한 번에 성공하거나 모두 실패한다.

배치 전에는 장소 효과 확정·턴 종료·카드 뽑기가 불가능하다. 카드 뽑기 후 active 선택은 닫지만 카포는 계속 자리를 점유한다. 서버 전용 `commitSpeakeasyLocationEconomy`와 `finishSpeakeasyLocation`은 장소 처리기가 허용 행동과 모든 추가 효과를 검증·해결한 뒤에만 호출한다. 이 hook은 클라이언트 명령이 아니며, 등록된 장소의 행동 큐 완료와 별개로 미지원 행동이나 도우미 효과를 해결했다고 보증하지 않는다. 레스토랑에는 별도 선택/완료 검사를 적용하며 일반 경제 hook으로 이를 우회할 수 없다.

라운드 정산 후 마피아 공개/소유자 방어/경찰/금고 지급을 같은 revision으로 진행한다. 지급 완료 전에 다음 막으로 넘어갈 수 없다. 다음 막에는 정산된 경제·운영 덱·차례를 유지하고 카포를 3/3/1개 회수한다. 동일한 카포의 제거 순서는 내부 목록 순서로 정하며 제거된 ID도 보존한다. 완료된 마피아 단계는 내부 history에 남겨 마피아 ID 재사용을 막는다. 금고·손패·미래 덱이 포함된 이 snapshot/history를 클라이언트로 보내면 안 된다.

동맹의 막별 일회성 효과 갱신은 개별 카드 능력 데이터 확인 후 추가해야 한다. 모든 동맹에 일괄 무료 사용을 부여하지 않는다. 이 연결 테스트는 예시 데이터로 **진행 순서**를 검사하며, 장소 효과를 모두 사용하는 공식 기본판 완주 검증은 아니다.

## 일반 장소 행동 연결

`domain/location-program.ts`는 서버가 확인한 자리별 행동을 줄 단위로 보관한다. `locationActions`는 카포 배치 시 등록된 구성을 복제하고 완료한 행동 ID를 기록한다. 현재 줄의 행동들은 원하는 순서로 처리할 수 있지만, 아래 줄은 앞 줄의 모든 행동을 실행하거나 건너뛰기 전에는 열리지 않는다. ID 중복, 없는 행동 완료, 앞 줄을 남긴 상태의 아래 줄 완료를 거절한다.

`application/location-command.ts`는 `EXECUTE_LOCATION_ACTION`, `SKIP_LOCATION_ACTION`, `FINISH_LOCATION_ACTIONS`를 기존 명령 서비스에 연결한다. 지원 종류는 장부 1개 획득, 유료 부하 고용, 건물 보호, 허용 종류의 운영 카드 사용, 최대 2회 건설/증축/인수, 생산·트럭 운송·판매, 허용된 운영/세력 수준 1 증가, 조직원 1명 획득이다. 종류·대상·사용 수량·현금 지불 선택만 요청받으며 가격, 무료 여부, 보호 비용표, 건설 허용 종류 및 카드 효과는 서버에서 결정한다. 보호는 현재 유효 차례 위치를 사용한다. 행동 큐를 마친 뒤 필수 카드 뽑기로 넘어가며 카포 점유는 막 종료까지 유지한다.

건설은 선택한 1–2개 배치를 순서대로 해결하면서 각 건물의 비용, 도시 타일 획득, 등록된 건물 보너스를 반영한다. 두 번째 건설 또는 보너스 실패 시 전체 명령을 commit하지 않는다. 미등록 건물 보너스를 무효과로 대체하지 않는다. 운영 카드는 기존 설치·교체/덱 아래 반환·상단 보너스·하단 행동 처리를 재사용한다. 여러 단계의 추가 선택이 해결되지 않은 효과는 이 완료 처리기에 성공으로 넘기면 안 된다.

생산량과 판매 한도는 서버의 5단계 표에서 현재 증류소/파티 수준으로 조회하고, 판매 단가는 현재 악명 5–25의 서버 표로 결정한다. 운송은 현재 함대 수준, 자리 보너스, 설치 중인 카드의 서버 보너스 및 보유 상자를 반영한다. 요청에는 이동·적재·하역·선박 구매 순서와 구매 수량/현금 지불 선택만 포함하며 가격·이동 범위·인접 그래프는 허용하지 않는다. 첫 지도 진입, 두 번째 트럭 해금, 트럭별 이동량·적재량, 건물 소유권/영업 상태를 검사하고 마지막 단계 실패도 전체 운송을 취소한다. `BUY`는 트럭과 선박의 같은 구역 여부, 수량 1–2, 적재 한도와 지불 가능 여부를 검사한다. 선박 재고를 오른쪽부터 가져오고 비면 공급을 사용하며, 구매 전체를 마친 뒤 시계 방향의 다음 빈 항구로 이동한다. 구매 뒤 후속 이동/하역이 실패해도 현금·금고·주류·선박 위치를 모두 되돌린다. 표와 지도는 검증한 서버 구성으로만 주입하며 시험용 수치를 공식 구성물로 배포하지 않는다.

`LEVEL`은 서버가 허용한 종류의 수준을 1 올린다. 운영 5/세력 4/세력 5 진입의 손패 1/1/2장 비용을 검사하고, 버린 카드를 해당 덱 아래로 반환한 뒤 도달한 악명 칸의 보상을 즉시 해결한다. 서버 `infamyBenefits`는 도달 가능한 칸마다 처리기 또는 보상 없음(`null`)을 명시해야 하며 미등록 칸은 거절한다. 처리기는 economy·city·decks만 받고 추가 플레이어 선택이 미해결이면 실패해야 한다. 카드 뽑기 보상도 비용 반환 이후 처리하며, 전체 인스턴스·도시 타일 정의·수준 보존을 검증한다. 실패/예외 시 지불·수준·보상·행동 완료 모두 원본을 유지하고 성공 시 revision은 한 번만 증가한다. 원작 보상 값이나 선택을 이 경계가 대신 생성하지 않는다.

`domain/family-actions.ts`의 `FAMILY`는 공급의 조직원을 VIP 또는 빈 부두 칸에 배치한다. 현재 VIP 수준의 서버 수용 한도와 서버에 등록된 부두 좌표를 검사한다. 부두는 신규 배치 보상을 먼저 해결한 뒤 요청한 순서대로 기존 본인 조직원을 빈칸으로 옮긴다. 신규 조직원·상대 조직원·점유 칸·미등록 칸은 거절하며 재배치는 추가 보상을 주지 않는다. VIP 선택에는 부두 이동을 붙일 수 없다. `dockBenefits`에 등록되지 않은 보상은 생략하지 않고 실패시킨다. 추가 선택이 완전히 해결된 서버 보상만 사용하며 전체 조각/카드/도시 타일 보존과 원자성을 검사한다. VIP 한도는 원본에서 확인한 기본 표를 사용하며 부두 보상 catalog와 실시간 선택 화면은 별도 연결 대상이다.

명령 서비스의 actor/phase/revision·직렬화·receipt 경계를 그대로 사용한다. 반환할 도시 타일이 있으면 필수 카드 뽑기 뒤 기존 반환 선택을 기다리고, 완료 후 다음 플레이어로 넘어간다. 내부 전체 행동 구성은 클라이언트에 보내지 않으며 `turn.locationActions`에는 행동 ID/종류/진행 상태와 현재 수신자의 완료 가능 여부만 제공한다. 이번 변경은 실시간 조작 화면을 추가하지 않는다.

원작 자리별 인원 제한과 전체 행동/보너스 catalog는 별도 검증 대상이다. 지원하는 일부 행동만 골라 원작의 한 자리 전체가 구현된 것으로 등록하면 안 된다. 시험용 전체 구성으로 일반 장소의 2인 22차례와 최종 정산 연결을 검사하며, 개별 도우미 효과 및 개별 악명 보상 데이터 등 미지원 효과는 계속 남아 있다.

## 보드 고정 장부 목표

`domain/fixed-goals.ts`는 규칙서 23쪽에서 확인한 부두·시청·악명 목표 9개의 조건과 금고 지급액을 정의한다. `player-command.ts`는 PLACE_BOOK 처리 시 이 목표들을 서버 내부에서 추가하므로 클라이언트나 외부 예시 catalog가 지급액을 정하지 않는다. 주입하는 `goals`는 해당 게임의 타일 목표이며 고정 목표와 ID가 충돌하면 전체 요청을 실패시킨다.

기존 장부 판정이 조건·빈 칸·자기 목표 중복·장부 재고를 검사하고, 레스토랑 행동 횟수와 revision 검증을 거쳐 금고 지급을 원자적으로 처리한다. 2/3/4인 명령 테스트에서 고정 목표 배치부터 필수 카드 뽑기와 다음 차례까지 연결한다. 타일 목표의 칸 보너스, 화면의 목표 목록과 게임 등록은 아직 연결해야 한다.

## 레스토랑 선택과 효과 처리

카포의 active 선택에 `restaurant` 진행 상태를 저장한다. 필수 입장 처리 이후 한 번에 한 행동만 열 수 있고, 완료한 종류는 다시 선택할 수 없다. 서로 다른 두 선택을 명시적으로 완료해야 턴 종료로 넘어간다. 선택 사항인 행동을 사용 없이 닫는 것도 허용하며 보너스를 받지 않는다. 상태 복원은 선택 중복, 횟수 초과, 미완료 상태에서의 카드 뽑기를 거부한다.

`restaurant-actions.ts`는 운영 카드 설치/동종 카드 반환 → 서버의 보너스 처리기 → 서버의 행동 처리기를 원자적으로 실행한다. 장부 명령에는 목표 ID와 칸만 받으며 조건·금액·보너스는 서버 catalog에서 찾는다. 장부를 하나씩 배치해 앞선 보너스가 다음 배치 조건에 반영되며 최대 3개 제한을 적용한다. 처리 실패 시 경제 상태·진행 횟수·revision이 유지되고, 경제 인스턴스 ID 보존도 검증한다.

개별 카드/목표의 보너스 처리기는 검증된 서버 코드로만 제공한다. 현재 처리기는 경제 상태 안에서 선택이 모두 해결되는 효과에 한정되며, 추가 카드 뽑기·사용자 후속 선택을 기다리는 효과의 continuation은 아직 필요하다. 도시 타일의 개별 ID·사용 횟수·전시장 반환은 아래 도시 타일 모듈로 연결했다. 개별 효과 catalog와 사용자 추가 선택은 아직 연결해야 한다. 미확인 catalog로 기본판을 활성화하지 않는다.

## 도시 타일 소유권과 턴 종료

`city-tiles.ts`와 게임 흐름의 `city` 상태는 개인판·사용 표시·중앙 열·오른쪽 열·뒤집힌 더미·건물 칸의 도시 타일을 고유 ID와 서버 effectId로 관리한다. 기존 경제의 `cityTileCount`는 실제 개인판 타일 수와 일치해야 한다. 사용한 타일은 반환 전까지 개인판에 남지만 사용 표시로 재사용을 차단한다. 기본판 최대 54개와 경제/카포/마피아를 포함한 ID 충돌을 검사한다.

도시 타일 명령은 actor·revision·현재 CITY_TILES 선택·본인 소유·최대 2개 제한을 검증한다. 서버 catalog의 효과 처리기가 경제와 도시 타일 상태를 함께 반환하며, ID·효과 식별자·사용 표시 보존을 확인한다. 처리 실패는 타일과 효과, 사용 횟수를 모두 보존한다. 이 행동 중 가져온 새 타일은 두 번째 사용 대상으로 고를 수 있다. 일반 카드 보너스에서 도시 타일을 얻는 연결은 별도로 필요하다.

오른쪽 열 획득은 명시적으로 고른 비어 있지 않은 뒤집힌 더미의 맨 위로 보충한다. 중앙 열은 맨 위 타일만 가져오며 보충하지 않는다. 보충 더미가 모두 소진된 경우는 규칙 미확정 항목으로 남겼다. 실제 54개 효과/장수 catalog와 지도별 배치는 아직 주입하지 않았으며 예시 값을 공식 데이터로 사용하지 않는다.

장소 선택과 필수 카드 뽑기를 마친 뒤 `awaitingCityReturn` 상태에서 사용한 타일과 선택한 초과분을 반환한다. 새로 뽑은 카드를 본 뒤 반환 타일을 고를 수 있다. 각 반환은 가장 짧은 중앙 더미를 선택하며 길이가 같으면 플레이어가 순서를 고른다. 잘못된 분배, 중복/타인 타일, 사용 타일 누락, 과다 버리기는 원자적으로 거절한다. 반환이 남아 있으면 현재 actor를 유지하고 추가 카드 뽑기와 다음 플레이어 진입을 차단한다. 반환 완료 시 다음 차례 또는 라운드 종료로 한 번만 전환한다. JSON 상태는 반환 대기를 그대로 복원한다. 이것은 내부 상태 검증이며 네트워크 재접속 UI 완성을 의미하지 않는다.

## 마피아 충돌에서 지역 정산까지

`domain/luciano.ts`는 `REVEAL → DEFENSE → REVEAL … → COPS → PAYOUT → COMPLETE` 전이를 구현한다. 설정 함수는 서버에서 확정한 덱·공격 예정 구역·경찰 예정 구역·배당표를 받으며 실제 기본판 데이터를 생성하지 않는다. 인원별 공격 구역 수, 기존 마피아 중복, 구역 유효성, 카드 ID 중복을 검증한다.

2인 폐쇄 구역은 마피아 공격 대상에서 제외하지만 경찰 예정 구역으로 허용한다. 경찰 배치 뒤에도 폐쇄 상태와 빈 건물 칸은 유지되며, 폐쇄 구역을 건설 가능한 구역으로 바꾸지 않는다. 경찰 구역 중복·범위 초과·기존 경찰과의 중복은 계속 거절한다.

각 공개는 한 구역에서 멈춘다. 그 구역에 건물이 있으면 차례순으로 방어 담당자를 정하고, 해당 플레이어는 자기 건물의 처리 순서를 선택할 수 있다. 요청에는 공격력이나 actor를 싣지 않는다. 인증 context의 actor, gameId와 revision, 현재 단계, 현재 방어 담당자와 대상 건물을 확인하고 비용·부하 소비·건물 교체·단계 변경을 함께 commit한다. 실패하면 원본과 revision은 유지한다. 같은 요청을 새 revision에 재적용할 수 없으며, transport의 성공 응답 재전송/idempotency receipt는 기존 Room 서비스에 연결할 때 추가한다.

다음 구역은 현재 구역을 완전히 해결한 뒤에만 공개한다. 이번 막에서 주점을 하나도 놓지 못한 신규 마피아는 제거 표시하고, 남은 신규 덱은 비공개 폐기 목록으로 옮긴다. 기존 마피아의 세력은 변경하지 않는다. 충돌 완료 후 예정된 경찰을 배치하고, 바뀐 영업 상태로 지역 지배를 계산해 금고에 한 번만 지급한다.

저장 가능한 내부 상태는 `parseSpeakeasyLuciano`로 검증·복원한다. `projectSpeakeasyLuciano`는 이미 공개한 마피아와 현재 선택 단계, 공개 건물 정보, 인증된 본인의 자금만 DTO로 재구성한다. 다음 마피아·버려지는 미사용 카드·다른 사람의 금고·손패·배당표 원본은 전송하지 않는다. 이 순수 복원 테스트는 실제 서버 재시작/Socket.IO 재접속 완성을 의미하지 않는다.

전체 게임 controller에는 막 진입 시 해당 동맹의 일회성 효과 갱신이 남아 있다. 다음 막의 구역·경찰 예약은 아래 자동 진행에서 연결한다. 카포 회수와 차례 진행은 `game-flow.ts`에서 처리한다. 해당 효과를 모든 동맹에 임의로 부여하지 않는다. 마피아 주점 24개가 부족하면 안전하게 중단하므로 관련 규칙 확인 전에는 이 모듈만으로 출시할 수 없다.

## 명령 이후 라운드·막 자동 진행

`application/advance-game.ts`는 플레이어 명령의 candidate에서 라운드 정산, 마피아 공개, 경찰 진입, 금고 지급, 다음 막의 카포 회수를 순서대로 처리한다. 다음 플레이어의 행동, 도시 타일 반환, 마피아 방어 또는 최종 결과에 도달하면 멈춘다. 방어를 서버가 대신 선택하거나 다음 마피아를 미리 공개하지 않는다.

게임 등록 시 1–3막의 구역·경찰·마피아 덱·배당표를 서버 전용 `actPlans`로 고정한다. 세 막의 수량, 중복 구역/인스턴스, 기존 구성물과 충돌을 검사하며 입력과 저장/조회 결과의 참조를 분리한다. 클라이언트 요청/응답에는 이 계획을 포함하지 않는다. 등록자는 확인한 실제 구성물 자료를 제공해야 하며 이 구현은 공식 catalog나 전체 초기 설정을 생성하지 않는다.

명령 서비스는 사용자 행동과 이어지는 자동 단계 전체를 한 candidate로 검증한 뒤 메모리 상태와 receipt를 한 번만 commit한다. 내부 단계마다 revision이 증가하므로 하나의 명령 응답에서 revision이 여러 단계 증가할 수 있다. 저장 버전은 한 번 증가하며 CAS와 인증 검사는 유지한다. 자동 처리 실패/예외 시 최초 행동까지 commit하지 않는다. 재전송은 정산을 반복하지 않고 기존 receipt와 최신 개인 응답을 반환한다. 최종 정산 뒤에는 새 행동을 거절하지만 결과 조회와 이미 성공한 요청의 재전송은 허용한다. 서버 재시작 복구나 영구 저장은 추가하지 않는다.

회귀 검증은 합성 초기 상태/구성물로 명령 서비스의 2인 22차례, 두 명의 연속 방어, 세 막 정산, 마지막 카지노 수익과 최종 결과까지 연결한다. 동시 마지막 카드 뽑기, 종료 후 재전송, 내부 계획 오류와 마피아 공급 부족 시 전체 rollback도 검사한다. 이는 실제 원작 구성물·일반 장소 행동·온라인 화면을 갖춘 한 판의 완성 검증은 아니다.

## 개인별 턴 화면 데이터

`application/turn-projector.ts`의 `projectSpeakeasyTurn`은 인증된 플레이어 ID를 받아 `SpeakeasyTurnViewSchema`로 검증한 턴 패널 DTO를 생성한다. 비참가자는 `null`을 받으며, 입력 내부 상태도 기존 복원 검증을 통과해야 한다. 모든 응답은 원본과 참조를 공유하지 않는다. 이 함수는 transport를 연결하거나 명령 권한을 부여하지 않는다.

카포 배치, 장소 행동, 레스토랑 선택/실행/완료, 필수 카드 뽑기, 도시 타일 반환, 라운드 종료, Luciano, 최종 정산을 구분한다. 레스토랑 두 선택을 완료한 상태는 새 선택 대기와 구분한다. 반환 대기에는 카드 뽑기 이전의 actor를 유지하고, 현재 actor의 응답에만 필수 반환 ID·초과분 후보·반환 수·첫 반환 가능 행을 보낸다. 첫 행 안내는 전체 반환 계획의 검증을 대체하지 않으며, 연속 반환의 행은 매번 바뀔 수 있다. 라운드/최종 정산에서는 actor가 없고 Luciano에서는 방어 담당자만 actor가 된다.

공개 부분은 차례·카포 점유·레스토랑 진행과 전시장의 맨 위 타일/더미 개수로 한정한다. 본인 손패·현금·금고·도시 타일·남은 카포는 `self`에만 넣는다. 타인의 손패·자금·보유 타일 내용, 덮인 도시 타일, 뒤집힌 보충 타일, 운영 덱 순서, 미래 마피아와 내부 history는 보내지 않는다. 상대 도시 타일의 공개 범위가 추가로 필요한지는 원본 자료 대조 후 확장한다. 이 보수적인 턴 패널 DTO는 전체 대국 보드 projection이 아니다.

복원된 동일 상태에서 동일한 DTO를 만드는 회귀 테스트는 구현했지만 실제 네트워크 재접속은 아직 연결하지 않았다. Socket.IO 호출자는 요청 본문의 viewer ID 대신 기존 인증 session의 player ID를 사용해야 하며, 플레이어별 응답을 전체 room에 broadcast하면 안 된다.

## 지도와 개인 경영판 응답

`application/board-projector.ts`의 `projectSpeakeasyBoard`는 검증된 게임 흐름에서 `SpeakeasyBoardViewSchema` 응답을 만든다. 기존 턴 패널과 현재 Luciano 응답을 같은 상태·revision으로 결합하고, 16개 구역의 빈 건물 칸 위치를 보존한다. 경찰·보호·주류 유무·영업 상태, 마피아가 점유한 칸과 공개 세력, 지도에 진입한 트럭의 위치/적재 개수, 부두와 장부의 좌표를 명시적으로 구성한다. 지도에 없는 상대 트럭과 화물 ID는 공개하지 않는다.

본인의 운영 수준·설치 카드·남은 건물·자원 수·주류/트럭·장부·상자·도우미·동맹 정보는 별도의 `self`에만 둔다. 타인의 개인판 전체나 내부 economy를 spread해서 보내지 않으며, 기존 턴 응답의 손패/현금/금고 제한도 유지한다. 예시 값이나 좌표를 새 규칙으로 만들지 않고 서버에 이미 검증되어 저장된 값을 표현한다.

최종 정산 전에는 `result`가 `null`이다. 마지막 라운드 정산을 마친 `FINAL_SCORING`에서만 점수 합계·건물/도우미 점수·동점 비교값·공동 승자를 기존 점수 함수로 계산한다. 종료 뒤에도 상대 손패, 금고 개별 내역과 숨겨진 카드 ID는 공개하지 않는다. 공개된 마피아 충돌 데이터는 기존 Luciano projection을 재사용하며 미래 덱과 과거 내부 history를 포함하지 않는다.

이것은 화면용 데이터 생성 단계다. 정확한 지도 연결·인쇄된 보너스와 구성물 catalog, 건물 칸 도시 타일의 공개 범위, 상대 개인판 공개 범위, 서비스·Socket.IO·대국 React 화면은 별도 연결이 남아 있다. 개발 미리보기는 이번 응답을 자동으로 구독하지 않는다. 인증 session에서 수신자 ID를 결정하여 플레이어별로 전송해야 한다.

## 응답 기반 지도·개인판 미리보기

`SpeakeasyBoardPanel.tsx`는 `SpeakeasyBoardView`를 받아 16개 구역과 본인 경영판을 렌더링한다. 영업 여부를 클라이언트에서 다시 판정하지 않고 응답의 칸 위치·경찰·보호·주류·영업 상태와 트럭 적재량을 표시한다. 구역 선택 상세, 운영 수준, 손패, 설치 카드, 자원 수와 공개 배치 개수를 제공한다. 금고는 처음에 가리며 게임/수신자가 바뀌거나 탭을 나갔다 돌아오면 공개 상태를 초기화한다. 이는 화면 가림이며 수신자별 서버 projection을 대신하는 보안 수단이 아니다.

`board-view.ts`는 strict DTO 스키마, 예상 game/viewer, 참가자와 구역 순서, Luciano의 수신자/revision 일치, 최종 정산 이전 결과 부재를 검사한다. 이 검증은 네트워크 인증이나 최신 revision 수신 제어를 대신하지 않는다. 향후 실시간 연결 시 기존 인증·재접속 경계를 적용해야 한다.

개발 미리보기의 **지도·개인판** 탭은 서버 projector로 만든 고정 예시 `board-preview.ts`를 검증해 전달한다. 공식 초기 배치나 덱 catalog가 아니며 서버 상태를 구독하지 않는다. 카포 배치·카드 사용 버튼과 game command 전송은 없다. 일반 대국 화면에 재사용할 때 고정 예시 안내를 실제 연결 상태에 맞게 분리해야 한다.

지도는 데스크톱 4열·작은 화면 2열의 구역 개요이며 도로 연결을 표현하지 않는다. 방향키는 시각적 열 수를 따르고 사용하지 않는 구역을 건너뛴다. Enter/Space로 선택하고 Escape로 취소한다. 모바일에는 선택한 상세로 스크롤·포커스를 이동하는 버튼을 제공한다. 선택·취소는 기존 효과음과 음소거/음량 설정을 사용하고 상태 수신만으로 소리를 재생하지 않는다.

## 실제 게임 연결 시 필수 경계

기존 Room/Session/UoW/직렬화/idempotency를 재사용한다. 게임 종류별 concrete service와 projector를 추가하며 다른 게임을 리팩터링하지 않는다. 서버는 actor, room/game phase, gameId/revision/turnId와 현재 허용된 선택을 확인한다. 인증된 명령은 비용·부가 효과를 포함한 candidate가 유효할 때 한 번만 commit한다.

추가 선택의 담당자와 남은 효과 순서를 서버에 보관한다. 마피아를 한 구역씩 공개하는 처리와 방어 선택을 같은 상태 전이로 관리한다. 카드 열람이나 다른 사람의 선택 이후에는 전체 턴 rollback을 제공하지 않는다. 금고·손패·덱 순서·미래 마피아는 공개 projection에 넣지 않는다.

## 플레이어 명령의 서버 준비 단계

`packages/shared/src/games/speakeasy/commands.ts`의 `SpeakeasyPlayerCommandSchema`는 지원하는 입력을 discriminated union으로 제한한다. 카포 배치, 레스토랑 선택/행동 완료, 운영 카드·도시 타일·장부 사용, 레스토랑 마무리, 필수 카드 뽑기, 도시 타일 반환과 마피아 방어를 구분하고 기존 명령별 strict 스키마를 재사용한다. 요청 actor, 계산한 economy, 보상/효과 handler, 정산·일반 장소 강제 종료는 허용하지 않는다. 이 계약은 아직 Socket.IO event나 게임 목록에 등록하지 않았다.

`application/player-command.ts`의 `prepareSpeakeasyPlayerCommand`는 인증 계층에서 전달한 actor와 서버 상태를 받아 참가 여부·gameId/revision을 검사하고, 복제·검증한 상태에서 기존 domain 함수를 호출한다. 운영 카드는 본인 손패에 있는 인스턴스에 연결된 서버 effect handler만 사용한다. 도시 타일과 장부도 서버 catalog로 처리하며 미등록 효과는 거절한다. 일반 장소는 해당 자리의 전체 행동 구성이 서버 catalog에 등록되어 있을 때만 카포를 배치할 수 있다. 미등록 자리는 계속 거절한다. 일반 장소 내부 완료 hook은 직접 노출하지 않고, 지원 명령이 행동 큐 완료와 actor를 검사한 뒤 호출한다.

성공 결과는 서버 전용 `candidate`와 요청자 전용 `actorView`를 분리한다. revision이 정확히 1 증가하고 결과 상태가 전체 복원 검사를 통과해야 준비가 성공한다. 원본은 성공·예상 실패·handler 예외 모두에서 유지된다. 예상된 명령 실패는 존재 여부를 구별하지 않는 `INVALID_ACTION`으로 통일하고, 서버 불변식/handler 오류는 호출 서비스의 내부 오류 경계로 전달한다. `candidate`를 wire 응답이나 room broadcast로 보내면 안 된다.

이 함수는 **순수 준비 단계**이며 저장·방/세션 인증·직렬화·idempotency receipt를 구현한 서비스가 아니다. 같은 원본에 병렬로 호출하여 얻은 두 candidate를 각각 저장해서는 안 된다. 향후 기존 Room serializer 안에서 최신 상태를 읽고, session/room phase 확인과 receipt 중복 처리를 거친 뒤 candidate와 receipt를 UoW로 원자적으로 저장해야 한다. 저장 성공 후에만 actorView를 전송하고 다른 참가자에게는 각자의 projection을 생성한다. 재전송 성공 응답·실제 재접속/이탈 검증도 그 연결 단계에 남아 있다.

## 명령 서비스와 개발용 원자적 저장

`application/command-service.ts`는 기존 `RoomMutationSerialExecutor` 인터페이스를 사용하여 같은 room의 읽기·명령 준비·저장을 직렬화한다. 입력은 공용 `SpeakeasyCommandRequestSchema`의 requestId와 행동이며, room/actor/현재 연결 권한은 인증된 호출 context에서 받는다. 비참가자·닫힌 게임·교체된 연결·다른 gameId·오래된 revision을 거절한다. 읽기 뒤와 원자적 저장 직전에도 현재 연결 권한을 다시 확인한다.

`ports/command-store.ts`는 상태와 성공 receipt를 한 번에 저장하는 경계다. 저장 버전을 비교하는 CAS로 다른 실행기가 동시에 접근한 경우도 덮어쓰지 못한다. requestId는 현재 game/actor 안에서 분류하고, 검증된 명령의 SHA-256 fingerprint를 비교한다. 객체의 키 순서는 무시하고 배열의 선택 순서는 보존한다. 같은 요청은 재실행하지 않으며 다른 내용으로 같은 requestId를 쓰면 `REQUEST_ID_REUSED`다. 실패·미저장 요청에는 성공 receipt를 남기지 않는다. 서버 오류는 비공개 원인 대신 `INTERNAL_ERROR`를 반환한다.

성공 응답에는 요청자 projection만 포함한다. 재전송의 `acceptedRevision`은 원래 승인 시점이며, `view`는 현재 상태에서 생성하고 `replayed`를 표시한다. 저장소나 서비스 인스턴스에서 읽은 내부 record/receipt를 전송하지 않는다. `snapshot`은 동일한 직렬화/권한 검사를 거쳐 현재 수신자의 화면만 생성하며 이전 명령이나 효과음을 재실행하지 않는다. 저장 직후 연결이 교체되어 응답이 차단돼도 새 연결에서 같은 requestId로 성공을 복구할 수 있다.

`infrastructure/in-memory-command-store.ts`는 주입된 검증 상태를 위한 **개발용 프로세스 메모리 저장소**다. 상태/receipt의 원자적 교체, 참조 분리, 저장 버전 증가, 닫기·제거를 구현했다. 제거 후 같은 room을 다시 추가해도 이전 저장 버전을 재사용하지 않는다. receipt는 해당 게임 제거 시 함께 제거된다. 생애주기 hook은 신뢰된 서버 코드에서 같은 room 실행기를 사용해야 한다. 공식 초기 배치를 만들지 않으며 앱 시작 코드·공통 Room 모델에 등록하지 않았다.

실제 플랫폼 연동에서는 이 포트의 adapter가 기존 Room/Session/idempotency/UoW와 **같은 원자적 commit**에 참여해야 한다. 공통 방과 별도 메모리 저장소에 나눠 쓰는 방식으로 연결하면 안 된다. 이 단계의 서비스 재생성 테스트는 동일 메모리 저장소에서의 복원을 검사하며 서버 프로세스 재시작을 넘는 영구 저장이나 실제 Socket.IO 재접속 완료를 의미하지 않는다. 공개 게임 종류, 실제 세션 검증과 연결 이벤트, 방 이탈/취소 정책 확정, 공식 catalog 연결은 남아 있다. 정산 자동 진행은 위 명령 이후 진행 단계에서 연결했다.

## 화면 및 소리

도시 타일 탭은 `SpeakeasyCityPreview.tsx`와 순수 `city-preview.ts`의 고정 예시다. 최대 2개 사용 → 운영 카드 확인 → 사용 타일·미사용 초과분 반환 → 다음 차례의 순서를 직접 조작한다. 선택만으로 사용하지 않으며, 가장 짧은 중앙 더미만 반환 대상으로 활성화한다. 사용 표시·단계 표시·남은 반환 수·완료 메시지를 소리와 함께 제공하고, 모바일에는 선택한 타일의 하단 확정 버튼을 둔다. Enter/Space 확정, Escape 취소, 단계 전환 시 제목 포커스, 모션 감소를 지원한다. 타일 사용·카드 뽑기·타일 반환 효과음은 기존 음소거/음량 설정을 공유한다. 빠른 연속 입력과 늦게 활성화되는 소리가 완료된 상태에 다시 적용되지 않도록 현재 상태와 음향 revision을 관리한다.

예시 타일 6개와 고정 PARTY 카드는 정식 catalog가 아니며 실제 효과·비용을 계산하지 않는다. 이 미리보기 reducer는 서버 규칙이나 멀티플레이 상태를 대체하지 않는다. 화면에도 이 제한을 명시한다.

오리지널 주점 일러스트, 지도 구역별 건물·경찰·조직원·주류, 세 가지 구역권, 내 운영 수준, 선택 및 결과 패널을 사용한다. 정확한 본판 지도 자료 확보 전에는 **구역 개요**로 표시하며 운송 인접을 암시하지 않는다. 숫자를 이미지에 박지 않고 접근 가능한 텍스트로 렌더링한다.

선택은 짧은 나무 클릭, 건설은 두 번의 낮은 타격, 운송은 짧은 이동음, 판매는 금속성 화음, 보호는 부드러운 잠금음, 정산은 저음 피아노 화음을 사용한다. Web Audio는 사용자 제스처 이후 활성화하고 음량·음소거를 제공한다. 실제 대국은 초기·동일·역순·건너뛴 revision 및 재접속에서 이전 효과음을 다시 재생하지 않아야 한다. 시각 결과는 소리 없이도 이해할 수 있어야 한다.

### 연습 행동 미리보기와 결과 표시

### 연습 길잡이와 구역 선택

`PracticeGuide.tsx`는 생산 → 운송 → 판매의 경제 흐름과 현재 가능한 선택 수를 보여 준다. 길잡이는 서버의 `choices`만 사용하고, 버튼은 해당 행동 목록/미리보기를 열 뿐 명령을 자동 확정하지 않는다. 행동을 모두 사용하면 턴 종료 확인으로 안내한다. 저장 주류나 트럭 적재가 남아 있으면 생산 반복을 권하지 않는다. 완료 이력을 저장하거나 보상을 추가하는 튜토리얼 규칙은 없다.

`practice-guide.ts`는 구역별 목록·개수·초기 탭을 같은 `preview.targets`로 산출한다. 단순 경유지는 행동 대상이 아니며, 생산은 실제 증류소가 있는 구역에서만 표시한다. 기존 탭에 해당 구역의 선택지가 없으면 가능한 탭을 연다. 전체 보기/길잡이 진입은 구역 필터와 이전 미리보기를 해제한다. 비용·행동 적법성·경제 상태는 계속 서버가 판정한다.

### 연습 개인 사업 현황

`PracticeBusiness.tsx`는 내 건물만 모아 위치·칸·주류·보호·영업 상태와 트럭 위치·적재량·남은 건물 공급을 보여 준다. 전체/현재 판매 가능/영업 중단/미보호 필터는 `practice-business.ts`가 공개 projection과 서버의 선택지로 산출한다. 주류 보유만으로 판매 가능을 추정하지 않으며, 행동 소진·대국 종료 시 행동 바로가기를 제공하지 않는다.

건물별 버튼은 정확한 `tileId`의 서버 선택지(생산은 서버가 명시한 구역/칸)를 기존 미리보기에 연결한다. 구역 필터를 해제하고 행동 종류·선택·포커스를 함께 이동하며 확정은 별도 입력이다. 동일 구역의 같은 종류 건물을 혼동하지 않고, 이동 경유지·건설 선택지를 기존 건물의 행동으로 붙이지 않는다. 새 대국은 패널 필터도 초기화한다. 점수나 경찰 규칙을 클라이언트에서 새로 판정하지 않는다.

### 연습 경찰·지역 정산 예고

`settlement` 응답은 다음 4/7/10턴 정산 시점·경찰 구역·본인의 영업 중단 위험 건물 ID·현재 배치 기준 금고 예상 수입을 담는다. 서버의 실제 정산과 같은 일정 및 수입 함수를 사용하고, 이미 배치된 경찰과 다음 경찰을 함께 반영한다. 10턴 정산 이후와 대국 종료 뒤에는 `null`이다. 상대 비공개 자원은 포함하지 않으며 미래의 건설·보호를 예측하지 않는다.

`PracticeSettlement.tsx`는 예상임을 명시하고 위험 건물의 정확한 칸을 표시한다. 보호는 서버가 제공한 해당 건물의 선택지로만 미리보기를 열며 자동 실행하지 않는다. 남은 행동이 없거나 보호 선택지가 없으면 안내만 표시한다. 현재 출시 범위와 남은 작업은 [로드맵](./SPEAKEASY_ROADMAP.md)에 정리한다.


## 고정 목표 화면

보드 응답의 `self.fixedGoals`는 본인의 고정 목표 9개 진행 수치·조건·지급액·두 장부 칸과 배치 가능 상태를 포함한다. 서버는 기존 목표 판정과 현재 레스토랑 행동 상태를 사용해 조건 미달·이미 달성·빈 칸 없음·장부 없음·장부 행동 필요·행동 한도 도달을 구분한다. 다른 플레이어의 진행 수치를 함께 보내지 않는다. 실제 명령은 기존 actor/revision/규칙 검증을 다시 통과해야 한다.

`FixedGoals.tsx`는 지도·개인판 미리보기에서 서버 응답 형식의 목표 카드를 표시한다. 클릭·Enter·Space로 세부 사유와 장부 칸을 펼치며 선택 효과음을 재사용한다. 좁은 화면에서는 한 열로 표시한다. 현재 고정 화면 예시이며 배치 명령 전송 버튼과 실시간 대국 연결은 남아 있다.


## 선박 상태와 공개 정보

경제 상태의 `ports`는 서버가 검증한 시계 방향 항구 구역 순서이고, `ships`는 고유 ID·현재 항구·왼쪽부터 채운 주류 ID 배열·왼쪽부터의 가격표다. 항구 중복, 선박 중복 점유, 항구 밖 선박, 재고보다 짧은 가격표와 조각 중복을 거절한다. 선박 이동을 위해 빈 항구가 하나 이상 있어야 한다. 기존 하위 경제/연습 상태는 빈 항구·선박 배열로 읽으며 원작 초기 선박을 자동 생성하지 않는다. 전체 경제/라운드/보너스의 인스턴스 보존 검사에 선박과 주류를 포함한다.

보드 projection에는 항구 순서, 선박 ID·항구·재고 개수·공개 가격만 전달하고 주류 인스턴스 ID는 제외한다. 실제 지도/가격 catalog 및 선박 조작 화면은 후속 연결 대상이다. 공급이 모자라는 구매는 현재 전체 실패로 처리하며 미확정 고갈 예외를 추정해 적용하지 않는다.


## 선박 공격

`AMBUSH`는 `domain/ship-ambush.ts`에서 같은 권역 조직원, 지불하여 빌린 상대 조직원, 소비할 부하를 검사한다. `cashToSpend`로 지불할 현금을 선택하고 나머지는 기존 지불 모듈의 금고 2:1 계산을 적용한다. 생략 시 보유 현금을 우선 사용하며 상대는 조직원당 현금 $1만 받는다. 고용 비용은 상자 수입 전에 충당해야 한다. 서버의 선박별 남은 주류 수 기준 방어력 표와 VIP 수준별 정원을 사용하며 공격력은 방어력을 초과해야 한다. 동맹 세력은 더하지 않는다. 상대 현금 지급·부하 반환·공식 상자 수입 계산/획득·상자 더미 교체·주류 배치·조직원 VIP/공급 복귀·빈 항구 이동을 기존 행동 큐의 단일 revision으로 처리한다. 실패하면 전부 취소한다.

선박의 선택적 `crate`와 비공개 `crateSupply`는 1–18 인쇄 번호를 사용한다. 공격 시 중복과 전체 상자 보존을 검사한다. 현재 선박 상자 번호만 공개 projection에 전달하고 다음 상자 더미는 숨긴다. 상자 또는 주류 공급 소진 예외가 확인되지 않았으므로 부족한 공격은 거절한다. 선박 주류를 임의로 보충하지 않는다. 11/12번 상자가 있으면 FAMILY 부두 선택의 `bonus`로 등록된 다른 칸의 보상을 선택할 수 있으며 실제 배치 위치는 바뀌지 않는다. 나머지 지속 효과는 기존 경제 규칙을 재사용한다.

실제 선박 초기 상자/더미 셔플·방어력/가격·항구 데이터와 공격 선택 UI는 후속 연결 대상이다. 테스트의 방어력 표와 배치는 합성 예시다.


## 도우미 획득과 사용

`HELPER` 장소 행동은 공개 진열대의 ID만 선택하고 같은 자리를 덱 맨 위 카드로 보충한다. 경제 상태의 helperDisplay/helperDeck 및 소유 카드 전체를 인스턴스 보존 검사에 포함하며 진열대/덱에는 사용된 카드가 있을 수 없다. 덱 소진 규칙이 미확정인 경우 획득 전체를 거절한다.

`USE_HELPER`는 자기 차례 PLAYING 단계에서 카포 배치 전에만 허용한다. `helperUses`의 막·라운드·플레이어·카드 기록으로 차례당 1장을 제한하고 카드 used 표시는 이후 모든 차례에 재사용을 막는다. 카포나 장소 행동을 소비하지 않으며 기존 actor/revision/receipt 경계를 따른다. 서버에 등록된 효과만 처리하고 추가 선택 미해결·실패·예외 시 사용 여부와 보상을 함께 취소한다. 사용 카드도 소유 카드로 보존하여 최종 병 점수에 포함한다.

공개 응답에는 진열 카드의 ID/병/값과 덱 장수만 보낸다. 본인에게만 소유 카드·사용 상태·카포 전 사용 가능한 ID를 전달하며 덱 순서와 다른 플레이어의 금고 뒤 카드는 보내지 않는다. 공식 도우미 catalog와 추가 선택 UI, 전체 초기 진열 설정은 후속 연결 대상이다.


## 카드 지불 추가 수준 증가

`PAID_LEVEL`은 서버 행동 구성에 명시된 VIP/PARTY/STILLS/FLEET 종류를 한 단계 올린다. 클라이언트는 버릴 손패 카드와 5 진입 시 추가 비용 카드만 선택한다. 종류가 다른 손패도 가능하며 설치 카드·상대 카드·중복 비용·초과 지불·최대 수준 초과는 거절한다. 이 아이콘으로 세력 수준을 올릴 수 없다. 선택하지 않으면 기존 행동 건너뛰기를 사용한다.

`raisePaidSpeakeasyLevel`이 추가 카드 지불과 기존 수준 진입 비용을 함께 검증한다. 이후 기존 수준 명령 처리기가 두 카드를 덱 아래로 반환한 다음 도달한 악명 칸 보상을 처리한다. 보상 실패/누락 시 비용·수준·행동 완료 모두 취소하며 성공은 단일 revision이다. 카드/도우미의 개별 복합 효과와 실제 자리별 배치는 검증된 catalog에서 이 효과를 조합해야 하며 자동으로 모든 수준 행동에 추가 기회를 부여하지 않는다.


## 도시 타일 획득과 상자 보유 한도

`CITY_TILE` 장소 행동은 가운데/오른쪽 열의 행 및 오른쪽 보충 더미만 입력받는다. 덮인 타일·비공개 타일 ID를 직접 선택할 수 없고, 가운데 열에 보충을 지정하거나 오른쪽 보충을 생략/고갈 더미로 지정하면 실패한다. 획득·보충·소유 개수·행동 완료는 단일 revision으로 반영한다. Park 교환의 상대 보상도 같은 진열대 획득 규칙을 사용한다.

`cityReturnsNeeded`와 `returnCityTiles`는 서버가 계산한 한도를 받는다. `speakeasyCityTileLimit`은 기본 4에 상자 7·8 각각 +1을 적용하며 game-flow의 상태 검증·필수 뽑기 뒤 반환 대기·실제 반환과 turn projection의 반환 수/선택 가능 타일 판정에 동일하게 사용한다. 사용한 타일은 항상 반환하고 미사용 타일만 증가한 한도 내에서 유지한다. 클라이언트는 한도를 지정할 수 없다.

기존 코드가 상자 보유자를 4개 한도로 반환 대기시키는 실패를 먼저 재현했다. 한도 5/6에서 다음 차례로 정상 진행, 초과 1개 반환, 사용한 2개 반환, 진열대 획득/보충과 비공개 ID 비노출을 검사한다.


## 공원 카포 교환

`EXCHANGE_CAPO`는 현재 플레이어의 사용 가능한 카포, 공원 밖의 상대 카포와 빈 공원 자리만 받는다. 서버는 상대 카포를 공원으로 옮기고 본인 카포를 해당 자리에 배치하며 등록된 장소 행동 큐를 연다. 대상이 레스토랑이면 기존 필수 카드 지불·빈 차례 칸 선택을 함께 검증한다. 미등록 장소·자기 카포·공원 카포·점유 공원·잘못된 비용은 이동과 지불 모두 취소한다. 교환은 카포를 추가로 소비하거나 상대의 배치 수를 늘리지 않는다.

교환 성공 후 `parkBenefit`은 옮겨진 상대의 선택을 기다린다. `CHOOSE_PARK_BENEFIT`만 허용하며 인증 actor가 보상 소유자인지 확인한다. `SKIP`으로 보상을 받지 않고 진행할 수도 있다. 영향력/장부는 1개, 도시 타일은 공개 진열대에서 1개를 가져온다. 보상 선택 실패 시 대기를 유지하고 재시도할 수 있다. 완료하면 원래 플레이어의 장소 행동으로 돌아가며 필수 턴 종료 뽑기는 기존 흐름을 따른다. 각 선택은 별도 revision을 갖고 기존 직렬화/receipt로 중복 반영을 막는다.

공개 응답의 `PARK_BENEFIT` 단계와 `parkBenefit`에는 보상 소유자·공원 자리·카포만 담는다. 이때 `actorId`는 보상 선택자이고 `active.playerId`는 교환한 턴의 플레이어다. 장소 완료 버튼 권한은 보상을 기다리는 동안 꺼진다. 다른 사람의 손패·소유 도시 타일·미래 보충 더미는 공개하지 않는다.

공원 보상은 자기 턴 밖에서도 도시 타일을 늘릴 수 있고 도우미는 카포 배치 전에도 타일을 줄 수 있으므로, `active`가 없다는 이유로 한도 초과 상태 전체를 거절하지 않는다. 소유자의 필수 카드 뽑기 뒤 기존 반환 단계에서 한도를 강제한다. 서비스 테스트에서 보상 수령 → 상대 턴 종료/라운드 전환 → 본인 다음 턴 → 초과 반환과 중복 요청을 검증한다. 실제 인원별 공원 자리 초기 설정 및 온라인 선택 UI는 별도 연결 대상이다.


## 확인한 VIP 기본 수치와 부두 지불 정정

Rules v19c 13쪽 VIP 그림의 전체 5개 값을 대조하여 `FAMILY`·`AMBUSH`의 서버 프로그램에서 `vipCapacityByLevel` 생략 시 `1/2/2/3/4`를 기본으로 사용한다. 서버가 명시한 시험용 표 주입은 유지하되 클라이언트 선택에는 한도 값을 받지 않는다. 생성 시 각 프로그램이 독립 배열을 갖는다. 생산·판매의 전체 표와 미확인 자리/부두 보상에는 기본값을 추가하지 않는다.

FAQ revised April 2026 1쪽은 금고를 이용한 부두 조직원 고용과 상대의 현금 $1 수령을 명시한다. 기존 현금 전용 판정을 회귀 테스트로 먼저 재현한 뒤 수정했다. 현금 부족 시 금고 사용, 명시적 전액 금고·혼합 지불, 비용 부족·위조 값 거절 및 후속 주류 공급 실패 시 양쪽 자금 원복을 검사한다. VIP 수준 1–5 각각의 조직원 획득 한도와 선박 공격 후 VIP/공급 복귀도 실제 확인 표로 검사한다.
